# The public API before 0.1.0 (2026-10-26)

0.1.0-preview.1 is on nuget.org, and any preview may still change the public API. This record goes through the whole
public surface (25 types in five assemblies, listed by reflection on the Release build) before it freezes, and says
what changes, what the owner decided and what stays as it is.

## Hidden: implementation detail, not API

Nothing outside the repository can sensibly depend on these, so they go `internal` without a question:

- **MJPEG's JPEG parsing types**: `JpegComponent`, `JpegFrameHeader`, `JpegMarker`, `JpegMarkerReader`,
  `JpegSegment`. `MjpegDecoder` is the API; the parser is how it works (the tests reach it through
  `InternalsVisibleTo`).
- **`PixelFormatExtensions.Of(chroma, bitDepth)`**: its `chroma` is H.264's chroma_format_idc, a codec detail in
  Core. The H.264 decoder and the tests use it.
- **`VideoFrame.IsDamaged`'s setter**: the H.264 decoder sets it; a consumer only reads it.
- **`AudioFrame.DropStart`**: the AAC decoder trims a frame's priming samples with it.
- **`VideoFramePool`**: each decoder keeps a pool of its own, which no API lets a caller pass or share, so a public
  pool serves only frames a caller allocates itself. Easier to make public later, with a way to hand it to a decoder,
  than to take back.

## Owner's decisions

Asked with the multiple-choice prompt; the owner took each proposal.

- **Namespaces.** `Mp4Demuxer`, `AviDemuxer` and `AdtsDemuxer` are in `ManagedCodecs.Containers.Mp4`, `.Avi` and
  `.Adts`, one public type each, under `Demuxer` in `ManagedCodecs.Containers`; the decoders are one level up
  (`ManagedCodecs.H264.H264Decoder`). The first install from nuget.org stumbled on it (#134 explains it in a README
  comment). **Decided: all three in `ManagedCodecs.Containers`.**
- **Audio timing.** `AudioFrame` has no `Pts`, so a consumer can't place audio against video without tracking the
  packets itself, and `IAudioDecoder` has neither `Flush` nor the async methods `IVideoDecoder` has (AAC holds no
  frames back, so `Flush` would return nothing today). **Decided: `AudioFrame.Pts`** (the packet's, moved by the
  samples skipped at its start), **and the interface as it is.**
- **A public API baseline.** `Microsoft.CodeAnalysis.PublicApiAnalyzers` with a `PublicAPI.Shipped.txt` and
  `PublicAPI.Unshipped.txt` per package, seeded from the surface after these changes: with `-warnaserror`, a pull
  request that adds, changes or removes a public member shows it in those files, and a release moves Unshipped into
  Shipped. **Decided: add it**, after the other changes. Shipped holds 0.1.0-preview.1's API, Unshipped what these
  changes did to it.

## Kept, and why

- **Raw arrays**: `VideoFrame.Planes`, `Strides` and `Offsets`, and `AudioFrame.Samples`, are arrays the caller can
  write. That is what zero-copy output (`ZeroCopy`, `BorrowFrames`) and a decoder's output without a copy need; the
  docs say which frames must not be written.
- **Each decoder's own `Decode(span)`**: MJPEG's returns one frame (one packet is one image), H.264's takes a pts and
  returns zero or more frames (reordering), AAC's returns one frame. They differ because the codecs do; the shared
  path is `Decode(Packet)` on the interfaces.
- **`IAudioDecoder.Decode(ReadOnlySpan<byte>)` on the interface**, where `IVideoDecoder` has none: H.264's span
  overload needs a pts, so a common video one would not fit.
- **The `VideoFrame` constructor that takes planes, strides and offsets**: the only way to wrap one's own buffers in
  a frame, and it checks that they hold the frame.
- **`ZeroCopy` (MJPEG) and `BorrowFrames` (H.264)**: two names because they promise different things: an MJPEG
  zero-copy frame stays valid, a borrowed H.264 frame only until the next call.
- **`IDemuxer` has one `Video` and one `Audio` stream**: a file with more streams gives the first of each. Not
  changing now; named here so that it is a decision, not an accident, before the freeze.
