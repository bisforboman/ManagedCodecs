# A Microsoft ADPCM decoder (2026-11-10)

After IMA ADPCM (docs/decisions/2026-11-10-ima-adpcm.md), the other ADPCM in .wav and AVI files is Microsoft's
(WAVE format tag 0x02): `WaveFormat` named it `"0x0002"` and the demuxers skipped it. Decided and built in one PR.

## The format, and what FFmpeg makes of it

A block holds a header of 7 bytes a channel (a predictor index, the step, the last two samples, the channels' fields
in turn), the two samples output first, then 4-bit codes, two a byte, the high nibble first (a stereo byte holds one
code of each channel). A sample is the last two weighted by the predictor's coefficient pair over 256, plus the code
times the step; the step then scales by the code's adaptation factor over 256, at least 16. FFmpeg's `adpcm_ms`
decodes it to 16 bits, which `-f f32le` turns into exactly x / 32768. Checked on hand-built blocks in a WAV file
(`MsAdpcmDecoderTests`) and FFmpeg's own files, it differs from the format's description in two ways:

- **Coefficients:** the WAVEFORMATEX lists the file's coefficient pairs (wNumCoef, then the pairs) after
  wSamplesPerBlock, and the format says to use them. FFmpeg never reads them: it always takes the standard seven, and
  refuses a predictor index past 6 ("block_predictor = 7"). A file whose second pair was changed to (300, -100)
  decodes, in FFmpeg, to the same samples as the original.
- **The step:** FFmpeg caps it at INT_MAX / 768, so that 768 times it (the largest factor) can't overflow. The format
  has no cap; a run of the largest codes reaches it from a step of 32767 in five codes.

Encoders write the standard table, so the two readings agree on every real file.

## Decided (the owner, 2026-11-10)

1. **Coefficients:** the standard table, as FFmpeg; the file's own is not read, and a predictor index past 6 is
   malformed. The decoder's output is FFmpeg's on every file, an altered table's too (a unit test).
2. **The cap:** FFmpeg's, with a mutation entry (it is FFmpeg's rule, not the format's).
3. **Name and place:** `CodecIds.AdpcmMs` (`"ADPCM_MS"`, as FFmpeg's `adpcm_ms`), given by `WaveFormat` at 4 bits, so
   in .wav and AVI files alike; `MsAdpcmDecoder : IAudioDecoder` in ManagedCodecs.Core beside `ImaAdpcmDecoder`, mono
   and stereo (the format defines no more). It cuts a packet of several blocks by wSamplesPerBlock, the first of the
   codec private data. `WavDemuxer` times its packets by its blocks (a block cut short by what it holds), as ffprobe
   does; `MediaPlayer` plays it, `mcdec` decodes it.

## Checks

- `wav-ms-adpcm` (mono, 1024-byte blocks: packets of 4) and `avi-mjpeg-ms-adpcm` (stereo, 512-byte blocks, a loud
  tone beside quiet ones): decoded exactly as FFmpeg (name.msadpcm.f32), packets as ffprobe's.
- Unit tests: hand-built blocks as FFmpeg decodes them in a WAV file (predictors 0, 1, 3 and 6, a negative step, a step
  driven to the cap, a block cut short), stereo's pairing, an altered coefficient table, malformed blocks.
