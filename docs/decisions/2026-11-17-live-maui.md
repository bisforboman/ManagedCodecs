# Live camera viewing in .NET MAUI (2026-11-17)

A plan, decided on by the owner (Decided, below): a sample, not a package, built after this note. Issue #526, point 4.
The Avalonia and WPF `LiveView`s are done (docs/decisions/2026-11-15-live-controls.md): each takes the newest frame of
a `LivePlayer` the application owns, on each frame the UI renders, copies it into a bitmap and draws it as `Image`
draws its source. This note asks the same of MAUI, which has two questions the desktop frameworks didn't: how to draw
a bitmap that changes every frame, and whether `LivePlayer`'s sockets and TLS work on Android, iOS, Mac Catalyst and
Windows.

## MAUI and ManagedCodecs.Playback

- A MAUI library targets `net10.0-android`, `net10.0-ios`, `net10.0-maccatalyst` and `net10.0-windows10.0.19041.0`.
  ManagedCodecs.Playback targets `net10.0`, which all four consume: no change to it.
- **The runtime differs.** On Android and on iOS and Mac Catalyst, .NET 10 runs on Mono (CoreCLR on Android is still
  a preview); iOS allows no JIT, so everything is compiled ahead of time by Mono's AOT. The decoders are checked under
  CoreCLR's JIT and Native AOT (`tools/aot-check.sh`) and under Unity's Mono 6.12, not under this Mono. Their SIMD paths
  fall back to scalar code where Mono doesn't accelerate a vector width. How fast H.264 decodes on a phone is unmeasured.
- `LivePlayer` decodes on a thread of its own, as on the desktop; the control copies on the UI thread.

## Drawing a bitmap that changes every frame

MAUI has no `WriteableBitmap` and no callback on each frame it renders. The options:

1. **`Image` with `ImageSource.FromStream`.** Each frame encoded (a BMP at least), then decoded again by the
   platform, with a new image source each time: an allocation and a decode per frame, and the flicker of a source
   swap. Not considered further.
2. **`GraphicsView` (Microsoft.Maui.Graphics).** Its `IImage` is made from an encoded stream; there is no
   cross-platform way to make one from raw pixels. Not considered further.
3. **SkiaSharp (`SkiaSharp.Views.Maui`'s `SKCanvasView`).** One implementation for all four: the frame copied into an
   `SKBitmap`, drawn on `PaintSurface`, the view invalidated per frame. Costs: a dependency with native binaries
   (libSkiaSharp, several MB per platform) and its own release cadence in the one-version coupling; the software canvas
   scales the picture on the CPU (its GL view does it on the GPU, but OpenGL is deprecated on Apple's platforms).
4. **A handler per platform** (MAUI's way to map a cross-platform `View` onto a native one), each doing steps 2 to 4
   of the desktop controls:
   - **Android**: an `ImageView` showing an `Android.Graphics.Bitmap` (`ARGB_8888`, whose bytes in memory are R, G, B,
     A: the frame's order, no swap), filled with `CopyPixelsFromBuffer`; paced by `Choreographer.PostFrameCallback`.
   - **iOS, Mac Catalyst** (one implementation): a `UIView` whose layer's `Contents` is a `CGImage` made from the
     frame's bytes (RGBA, alpha skipped); a new `CGImage` per shown frame, as Core Animation takes them immutable;
     paced by `CADisplayLink`.
   - **Windows**: WinUI's `Image` with its `WriteableBitmap` (BGRA: red and blue swapped, as in WPF); paced by
     `CompositionTarget.Rendering`.

   The scaling is the platform compositor's (on the GPU); no dependency beyond MAUI itself. Three implementations
   instead of one, of about 50 lines each.

Either way the control would have MAUI's names, not Avalonia's: `Aspect` (`AspectFit`, `AspectFill`, `Fill`,
`Center`, as MAUI's `Image`) in place of `Stretch`, with `Player` and `ShownFrames` as on the desktop.

## Sockets and TLS on each platform

What `LivePlayer` uses: `TcpClient` (RTSP, RTSP over HTTP), `Socket` for UDP (RTP unicast and multicast), `SslStream`
with a validation callback (RTSPS: the system's trust, or a pinned SHA-256 of the certificate), and an `HttpClient`
(MJPEG over HTTP; the caller's own, or one the player makes). From the platforms' documentation; none of it has been
run on a device or emulator.

| | Android | iOS | Mac Catalyst | Windows |
|---|---|---|---|---|
| TCP (RTSP) | Works; `INTERNET` permission (MAUI's template has it) | Works; on the local network, iOS asks the user first (`NSLocalNetworkUsageDescription` in Info.plist, or the connection fails) | As iOS, plus the sandbox's `com.apple.security.network.client` entitlement | Works, as in WPF (a MAUI app on Windows is full trust, not network-isolated) |
| UDP unicast (RTP) | Works | Works (local network prompt as above) | Needs `com.apple.security.network.server` too (bound ports receive) | Works; the firewall may ask once |
| UDP multicast | Filtered by the Wi-Fi driver unless the app holds a `WifiManager.MulticastLock` (`CHANGE_WIFI_MULTICAST_STATE`) | Needs Apple's `com.apple.developer.networking.multicast` entitlement, granted on request | As iOS | Works |
| TLS (RTSPS, pin) | `SslStream` runs on Android's own TLS (Java's `SSLEngine`); the callback gets the certificate, so the pin works | `SslStream` runs on Apple's Security framework; the callback runs, so the pin works; TLS 1.2 at most there unless .NET 10's Network.framework path is turned on (a camera that offers only TLS 1.3 would fail) | As iOS | Schannel, as in WPF |
| HTTP (MJPEG, `http://`) | A plain `HttpClient` uses Android's handler in a MAUI app, which refuses clear text from Android 9 unless the manifest allows it (`usesCleartextTraffic` or a network security config); a `SocketsHttpHandler` client doesn't | `HttpClient` uses `NSUrlSession`, which App Transport Security blocks for `http://` unless Info.plist allows it (`NSAllowsLocalNetworking` for cameras on the local network) | As iOS | Works |
| In the background | Keeps running while the process does | Sockets are suspended within seconds; the player sees errors and reconnects (`Reconnecting`) when the app returns | Keeps running | Keeps running |

So the code works everywhere; what differs is what the application declares. The package can't set an app's manifest
or entitlements: its page (PACKAGE.md) and the sample would list them per platform. One change to consider in
Playback, not needed for MAUI: a default `HttpClient` built on `SocketsHttpHandler` (as on the desktop), which skips
Android's and Apple's clear-text rules for MJPEG; the platform handlers are what an app's own proxy and trust settings
go through, so leaving the choice to the caller (`MjpegHttpSource(Uri, HttpClient)`) is the other way.

## Building and testing

**In this Linux container** (a cloud session):

- `dotnet workload install maui-android` works (through the session's proxy). Linux offers no iOS or Mac Catalyst
  workload (they need macOS and Xcode), and the Windows target needs Windows (WinUI's build tasks).
- A MAUI app referencing ManagedCodecs.Playback restores, but its Android build stops at `XA5300` (no Android SDK):
  the SDK comes from dl.google.com, which this environment's network policy refuses. With that host allowed, the
  Android target would build here (`-t:InstallAndroidDependencies`); nothing would run (no emulator, no KVM, no
  device).
- What can be tested here is the platform-free part: the scaling arithmetic and the frame-pacing logic, if kept in
  plain `net10.0` code.

**In CI** (none of it there today; all on GitHub's hosted runners, none required, like windows.yml):

- **Android**: ubuntu runners have the Android SDK and KVM, so an emulator can run a test app against a loopback MJPEG
  server and compare what the control drew with the decoded frame, as `LiveViewTests` does for Avalonia headless. The
  heaviest job: the emulator takes minutes to boot.
- **iOS, Mac Catalyst**: a macOS runner builds both; a Mac Catalyst app runs on the runner itself (no simulator), the
  cheapest real check of the Apple handler and of the sandbox entitlements. The iOS simulator can run too, slower.
- **Windows**: windows.yml's runner, as `mclive-wpf --frames`.
- **Packing**: a package with all four targets needs one machine that builds them all. Linux can't (release.yml runs
  on ubuntu); Windows or macOS can (an iOS class library needs no Mac unless it links native code: to be checked). The
  release would get a job of its own on one of them for this package.
- **Versions**: MAUI ships with each .NET, yearly, and each MAUI version is supported for a shorter time than .NET 10's
  long-term support. A package built on MAUI 10 has to move to MAUI 11 within about a year, which is SDK 11, which this
  repository defers to a pull request of its own (global.json). Every package ships at one version, so that move is a
  new version of all of them.

## Sound

MAUI has no way to play raw samples either (the community toolkit's `MediaElement` plays files and URLs, not a
stream of PCM). Not covered, as for Avalonia and WPF.

## Proposal

1. **What to build** (decision 1): a sample, not a package (recommended). `tools/ManagedCodecs.Maui.Sample`: a page
   with the view and its handlers, the manifest and entitlements each platform needs, built in CI. An application
   copies the handlers (about 200 lines); no public API, no MAUI version in the package set, and the sockets and TLS
   rows above get checked on real platforms. A package can follow when someone asks, from code that has run.
2. **How to draw** (decision 2): a handler per platform (recommended): no native dependency, the compositor scales.
3. **Which platforms first** (decision 3): Android and Windows (recommended), the two whose runners run the app with
   the least setup, then iOS and Mac Catalyst on a macOS runner.

## Decided

Asked with the multiple-choice prompt (2026-11-17): the recommended option each time, 1 (a), 2 (a) and 3 (a). The
options, recommended first:

1. **What to build. Decided: (a), a sample.**
   - **(a) A sample, not a package** (recommended): above.
   - (b) A package, `ManagedCodecs.Maui`, with a `LiveView`, PublicAPI files, package validation (no baseline until its
     first release) and a release job on Windows or macOS to pack it.
   - (c) Neither yet: wait for someone to ask, as #462's survey advised for the desktop controls.
2. **How to draw. Decided: (a), a handler per platform.**
   - **(a) A handler per platform** (recommended).
   - (b) SkiaSharp's `SKCanvasView`: one implementation, a native dependency.
3. **Which platforms first. Decided: (a), Android and Windows.**
   - **(a) Android and Windows, then iOS and Mac Catalyst** (recommended).
   - (b) All four at once.
   - (c) Mac Catalyst and Windows first (the two that run on hosted runners without an emulator or simulator).
